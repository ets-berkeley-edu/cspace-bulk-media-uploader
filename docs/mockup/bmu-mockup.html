Sensitivity and publishing More
    Three different things: the museum's sensitivity of an object, the publish setting of each image, and the BMU's protected file handling while the file is in the BMU. The Public portal column combines the first two. None of them stops CollectionSpace users who can read the record from seeing the image.
    Protected files
    A protected file gets no stored thumbnail, only a locked preview for others, early cleanup in the BMU, and a “don't publish” default. The BMU decides this itself from the tenant's configuration and CollectionSpace: documents linked to an object the museum marks sensitive are protected automatically. There is no manual setting.
    Group
    When on, the job creates one new group and every document linked to an object joins it once its Media record is linked; untick a document's Group box to leave it out. Documents that aren't linked to an object can't join.

    Notes for reviewers

    • What changed from v1: the Handling list, the publish column, the editable fields and the sample files now differ per tenant. Choosing a handling sets the Media record's identification number rule, whether it links to an object, and pre-filled field values (marked PRESET). Presets only replace fields you haven't edited yourself.
    • Handling options per tenant follow each tenant's current BMU options, plus PAHMA's new “Link to object (create if missing)”: PAHMA has four, the Botanical Garden adds born-digital but has no “create object”, UCJEPS has five including slide and born-digital, and BAMPFA and Cinefiles only link to existing objects, so their Handling column is read-only. “Create new object + link” only creates: if the object already exists (try 15-1234), the document must be fixed by switching to a handling that links or correcting the object number. “Link to object (create if missing)” links when the object exists and creates it otherwise. In Finished jobs, a document that failed with “Object already exists” can switch its handling, but only to one that links.
    • Publish column matches each tenant's own field: a checkbox for PAHMA, yes/no for the Botanical Garden and UCJEPS, and a three-level website display choice for BAMPFA and Cinefiles (marked pending, since mapping it is an open decision). Botanical Garden label images are locked to “No”.
    • Creator, contributor, rights holder are autocomplete fields: type 3 or more characters, and the search runs after the tenant's find delay (1 second at PAHMA, as in its CollectionSpace UI). Like PAHMA's UI, they search local Persons and Organizations: the UI's source list also names “shared” vocabularies, but none is configured, so they're skipped. The sample Person authority is the list of US presidents and the sample Organization authority is the University of California campuses; results are grouped by source. Contributor presets (Botanical Garden, UCJEPS) use UC Berkeley so they point to a term in the sample authority. Only existing terms can be chosen; there's no “add new term”. The same holds for every list in the BMU: option lists, vocabularies and authorities only offer existing values, and missing values are added in CollectionSpace.
    • Creator initials (Botanical Garden): a pane at the top of the Create / edit tab lists the mappings from filename initials to Person or Organization terms and checks each term against CollectionSpace (Valid, Name changed, Not found; “Not checked” for users who can't read the authorities). Users allowed to change the Person and Organization authorities can edit, add, deactivate or remove mappings; everyone else sees them read-only. Saving updates the Creator of documents in the open job that you haven't edited yourself, and is written to the audit log. Try the “Signed-in user” switch to see the read-only and not-checked views.
    • Audit log (future feature): at the bottom of the Finished jobs tab, collapsed until you open it. It lists every submitted job, run, cancelled or completed run, move to Drafts, draft takeover, row deletion and job deletion for the tenant; drafts, finished jobs and saved sign-ins that expired, reverted fixes and removed protected files; creator initials changes; and every change to the job schedule, queue order or a queued job’s run settings (Run now, run time, hold), newest first, for about a year, even after the jobs are gone; filter by event, search by job, user, filename or CSID, sort any column, and open an entry's CSIDs. This view is not in the first release and isn't a priority; the audit log itself is recorded from day one.
    • Uploads: new files upload in the background while you edit. A row's Status shows “Uploading 35%” with a bar, then “Verifying”, then its normal checks; a failed upload shows Retry and Remove. The line above the table counts them. A draft can be saved while files upload, but the job can't be submitted until every file is uploaded and verified. A running job in the Job queue shows done, failed and remaining documents with a bar and the document in progress. Only JPEG, TIFF, PNG, PDF, WAV, MP3, AAC, MP4 and X3D files are added, for every tenant, up to 2 GB each; other files, and files over 2 GB, are skipped with a message naming them.
    • Protected files (the BMU's own handling flag, formerly “Sensitive”): set only automatically, when the tenant's configuration and CollectionSpace data show the object is sensitive to the museum; users can't set or clear it. Only some rules also hide every image of the object on the public portal (PAHMA sample 3-4567, “culturally” with Human Remains); other protected files (PAHMA sample 12-5678, NAGPRA) follow the image's own publish setting, with a warning if it would publish them. The “Sensitivity and publishing” panel above the job explains each museum's rules, and the Public portal column shows whether each image will appear publicly. Their filenames stay visible to everyone; only the preview is restricted (see Thumbnails). A softer signal (PAHMA sample 15-1240, a restriction at the “recommendation” level) is a warning suggesting you withhold the image; once you do, it stays on the row as information. A protected file's upload is deleted from the BMU 7 days after its job stopped; if the document still needs it, Fix and reschedule asks for the file again with Replace file (PAHMA finished job “consultation photos, box 3”).
    • Jobs that collide in the queue: not simulated in this mockup. In the BMU, a job is also checked against the jobs ahead of it in the queue. A “Create new object + link” document whose object an earlier job creates first is “Must fix” (the earlier job would create the object, and this document would then fail); the message names the other job and offers “Link to object (create if missing)”. A document with the same identification number as one in an earlier job gets a warning. In the Job queue, a staff member who moves a job, or uses Run now, Hold or a run time, in a way that would make a document fail is told which document and asked first (“Move anyway” or Cancel), in the row under the job. If they go ahead, the job that would fail shows “needs fixing” at once in “Checks now”, and a box above the list names the documents and offers Reorder to avoid failures… to staff, which says what it will move before moving it.
    • Queue safeguards: each queued job shows how long its saved sign-in lasts, with a warning when it's close to the 72-hour limit; a job that runs out moves to Drafts with a note (see “weekend imaging batch”). Edit on a queued job first warns that it leaves the queue and loses its sign-in. A running job has Cancel run: it stops after the document in progress and appears in Finished jobs as needing attention. In Drafts, the expiry column says whether a draft will be deleted or, for a fix of a job that already ran, reverted.
    • Group: tick “Create a group of this job’s objects” to have the job create one new group; the title is required and starts empty. Type one, or use “Use the job name” (the job name exactly as typed) or “Use a timestamp” (bmu-YYYY-MM-DD-HH-MM-SS, Pacific time, like the legacy BMU's =job title); changing the job name later doesn't change the title. Every document linked to an object is in the group by default; untick its Group box (or use the side panel) to leave it out. An object joins only after its document's Media record is created and linked, so a document whose Media record failed adds nothing to the group. Reruns reuse the same group. Once a run has created the group, reopening the job (Fix and reschedule, Reschedule or Edit) locks “Create a group” and the title, with a note saying which run created it (try “collections survey batch 4”).
    • Editable Media fields per tenant are the fields each tenant's current BMU form offers, plus the values the current BMU fills in automatically per handling option (media type, contributor, copyright), which become editable presets. PAHMA's automatic values are blank today, so its media type, contributor and copyright start empty; BAMPFA and Cinefiles have no form fields, so they edit only Language.
    • Language is sent on every record, as today, and defaults to English (tenant configuration). It can be changed or given more than one value; the sample list stands in for the tenant's languages vocabulary in CollectionSpace.
    • Media type can have more than one value, as in CollectionSpace. Each tenant's list, order and display labels match its UCB UI configuration (the stored value can differ from the label, e.g. still_image shown as “still image”); the real BMU loads them from that configuration.
    • Simulated: object lookups, “found in CollectionSpace”, sensitivity flags, duplicate-ID warnings, filename parsing and all list values are hard-coded samples for this mockup only. Born-digital numbers use the DP- convention with a per-tenant counter (DP-2026-001042); the table shows a preview, and the final numbers are reserved when the job is submitted.
    • Thumbnails: every document row in the editor, previews, results and expanded job rows starts with a thumbnail; click it for a larger view (Esc or Close to dismiss). Here they are drawn stand-ins by file type (object photo, label, TIFF, audio, video, 3D model). In the real BMU the browser makes the thumbnail for JPEG and PNG, the server makes one for TIFF, and video, audio and 3D files show a type icon; thumbnails carry no EXIF or GPS data and are served only through the web app. A BMU thumbnail is deleted once its file is in CollectionSpace, and from then on CollectionSpace's own derivative is shown (hover a thumbnail to see which). Protected files (🔒) get no stored thumbnail: the person who added the file sees a local preview in their own browser, and everyone else sees a lock until the file is in CollectionSpace, whose derivative is then shown only to users allowed to read the record. Save and reopen a draft, or switch the signed-in user, to see the difference.
    • Layout: the “change selected documents” controls sit in a panel to the left of the document table and stay in view while you scroll, with a count of how many documents are selected. The arrow button in its header slides it closed to a slim rail that shows how many documents are selected, giving the table more room; the same button, or a click anywhere on the rail, slides it open again. The page remembers your choice. On narrow screens the panel moves above the table.
    • Large jobs: jobs can hold up to 1,000 documents, so the editor, job previews and job results show them in pages (25, 50 or 100 per page) with first / previous / next / last controls above and below the table. Click a column heading to sort (ascending, descending, then back to the original order); every table on every tab sorts this way, including the Drafts, Job queue and Finished jobs lists and the documents shown in an expanded job. Sorting the job queue only changes the view: the queue still runs in its own order, and dragging is off until the sort is cleared; a “Show” filter narrows to documents that need fixing, have warnings, are protected files, excluded or selected (in results: failed, partial, not started, excluded, done). The header checkbox selects the documents on the current page, with a link to select every matching document; bulk changes apply to everything selected, on any page. Try it with “Load 1,000 sample documents” in the bar at the top, or the “2026 digitization project, batch 1” job in Finished jobs. Expanded rows in the job lists show the 10 most important documents; the full preview or results shows them all.
    • Sign-in: the mockup opens on the sign-in screen, like the BMU. The BMU checks the username and password against CollectionSpace (Basic Auth) and reads the account's permissions and roles; here any username and password work, the password “wrong” shows a rejected sign-in, and the tenant, permissions and BMU role (staff or intern) are picked on the sign-in screen. Your username (top right) opens a menu, as in the BMU: Dark mode or Light mode (the choice is remembered in this browser; until you make one, your system's setting decides) and Sign out. Signing out stops editing the open draft; it stays in Drafts, saved, since every change is saved as it's made. Submitted jobs keep running after you sign out: each keeps its own sign-in until it finishes. The Mockup settings pane collapses to one line with the triangle at its left.
    • Roles: every BMU user has one of two CollectionSpace roles, which carry no permissions and only tell the BMU what the user may do. BMU_Staff do everything: edit any draft, submit jobs, change the schedule and the queue (reorder, Run now, run time, hold, pause), cancel any run, and fix or delete finished jobs. A BMU_Intern creates drafts and edits the drafts marked “Open to interns” (a draft an intern created; a staff member's is “Staff only”); an intern can't submit, can't take over a draft a staff member is editing, can't delete a draft that has already run, and sees the Job queue and Finished jobs without changing them. The header shows “Intern”. A user with neither role, or a staff account missing the permissions the BMU exists to use, is refused at sign-in with a message to contact their CollectionSpace administrator (not simulated here). Try it with the “BMU_Staff role” box in Mockup settings or on the sign-in screen: unticked, you are an intern. In Drafts, staff switch a draft between “Open to interns” and “Staff only” with one click (in the BMU the Create / edit job page has the same switch as a checkbox, not shown here), and an intern uses Hand over to staff… to give a draft that is ready to staff: it becomes staff only. Staff can also Submit… a draft from the list or its preview without opening it, when nothing needs fixing; the confirmation says how many documents it has, who created and last saved it, and that it runs with the submitter's sign-in. In the Job queue, Move to Drafts… takes a queued job out of the queue like Edit, but without opening it.
    • Three kinds of result: the BMU never presents a permission problem as a mistake in the job. A check on a document ends one of three ways. Needs fixing (red) is a problem with the job, such as a wrong object number, for whoever edits the draft. Needs an Object creator (purple) means the document would create a new Object and the signed-in user can't create Objects: it is counted separately (“nothing to fix · 3 need an Object creator”), the job says so in one line at the top, and the handling list still offers “Create new object + link”, with a note, so anyone can prepare a job for a colleague. That user can't submit those documents, but Submit without the 3 documents that need a new Object submits the rest: the documents left out stay in the job, excluded and marked, and when the run ends the job waits under Finished jobs as “Waiting for someone who can create Objects” for a colleague's Fix and reschedule. A problem with your account (creating groups is the only one left after sign-in) is said once, beside the group, with a line to contact the CollectionSpace administrator; nothing is marked on the documents and only Submit is stopped. An intern is never told about their own permissions: they act for whoever submits, and see only that a document needs a new Object. Try it with the Permissions switch set to “Imaging staff” (can't create objects) or “Registrar assistant” (can't create groups), and a file named for an object that doesn't exist, such as 20-0990_1.jpg, with “Link to object (create if missing)”.
    • Interns' checks: an intern's CollectionSpace account has no permissions, so the BMU makes the lookups an intern's draft needs (is the object there, is it protected, does a Media record with this number exist, authority terms, languages, dates) with one read-only CollectionSpace account per museum (role BMU_Reader). Its password is kept in AWS Secrets Manager, where only the web app can read it; staff always use their own sign-in, and every record is created with the submitting staff member's. An intern gets minimal answers: whether the object was found and whether the file is protected, but not why (“marked sensitive in CollectionSpace”), not the object's access notes (“a note about access in CollectionSpace”), and never a record's contents or images. Lookups are logged for each intern and limited per hour. Untick “BMU_Staff role” and add the sample files 3-4567 or 15-1240 to see the difference.
    • Job lists: Drafts, Job queue and Finished jobs show one line per job. The triangle at the start of a row expands it in place to show the job's details (handling mix, group, who and when, expiry or run history) and one line per document with its status and most important problem or result, with a link to the full preview or results. “Expand all / Collapse all” sits above each list; hover over dates and badges for who did what. In Drafts and the Job queue, a job's confirmation (Delete, Edit, Cancel run, Take over) opens in a full-width row under the job, where its text has room.
    • Worked example: in Finished jobs, open “example: fixed by excluding a document” with View results. Its run history shows run 1 needing attention because one document's Media record was rejected, that document then excluded by jdoe, and run 2 completing with the document shown as excluded. To try it yourself: use Fix and reschedule on “collections survey batch 4”, check Exclude for the documents that need fixing, press Submit job, then in the Job queue use Run now on it and Finish run (mockup) on the running jobs until it has run.
    • Excluding documents: the Exclude checkbox at the end of each row (unchecked by default; hover its heading for “To exclude a document from a job, check the box.”) tells the BMU to ignore a document, for example one with a problem that can't be fixed yet. Excluded rows are grayed out, their fields can't be changed, and they are left out of the checks, so they never block submitting; unchecking Exclude restores the row as it was. Exclude selected / Include selected in the side panel work on several rows at once. Done rows have nothing to ignore. Deleting documents: the trash button at the very end of each row (after Exclude) deletes that document from the job permanently, after a confirmation in the row; its uploaded file is removed and nothing in CollectionSpace is touched. Delete selected, under Exclude selected / Include selected in the side panel, does the same for all selected documents after a confirmation in the panel. Excluded documents can be deleted too. Only documents that haven't created anything in CollectionSpace, and that the last run didn't stop on while working on them (BAMPFA's “loan documentation”), can be deleted (finding an existing object doesn't count): for the others the trash button is disabled, its tooltip and the expanded row explain why, Delete selected leaves them in place and says how many it skipped, and they can only be excluded. Deleting the job's last document, or every document at once, deletes the job too. Each deleted document is written to the audit log (Row deleted). In the BMU a document shows “Deleting…” in its Status, and Delete selected reads “Deleting…”, until the server has removed it; this mockup deletes at once. A partial row can be excluded too; its Media record stays in CollectionSpace, unfinished.
    • Finished jobs: jobs that have run, with their outcome (Completed, Needs attention, Failed), how many documents were done, partial, failed or not started, and who ran them. View results shows every document's steps with the CSIDs created, and for each failure a plain explanation, what to do, and the technical detail on request. Fix and reschedule (or just Reschedule, when every failure only needs another run, such as a sign-in failure, an outage or a cancelled run) moves a job that needs attention or failed into Drafts: documents already created are read-only (🔒), a partial document shows why its fields are locked (its Media record already exists, and the BMU never updates records; change them in CollectionSpace instead) and only allows what the rerun still needs: a corrected object number, a replacement file, stopping the link to an object, or leaving the job's group (untick Group while its Add to group step hasn't been done; the rerun then shows that step as not needed), and submitting queues a rerun that skips everything already done. The BMU checks every document against CollectionSpace again just before creating anything for it: its values (renamed terms are used under their current names, with a notice), the permissions its handling needs, its object and its file. A document that fails this check (a value that no longer exists, an object that is gone or that now exists for “Create new object + link”, a missing permission) has nothing created for it, while the rest of the job goes on: in its results, the first step, Check the document in CollectionSpace, failed and the other steps were skipped. Completed jobs are removed after 30 days.
    • Drafts: Save draft keeps a job at any stage, even incomplete or with documents that need fixing, under the Drafts tab. Everyone signed in to the tenant can see and edit drafts, one person at a time: opening a draft shows it as “being edited by” that person. Others can preview it, or take it over after a warning; the first person's page then becomes read-only. Every change is saved as it's made, so closing a draft or starting a new job needs no prompt. In the BMU the draft being edited is part of the page's address, so reloading the page (or a bookmark) reopens it; this mockup starts over when reloaded. Editing a queued job moves it to Drafts until it is submitted again. Drafts expire 30 days after they were last changed or saved, or 7 days if any document is a protected file; the Drafts tab shows each expiry date and highlights those due within 3 days.
    • Job queue: name the job and press Submit job. If nothing needs fixing, the whole job is checked again and moved to the Job queue tab, and the editor starts a new, empty job. “+ New job” at the right of the tabs starts one at any time (the current job stays in Drafts); in this mockup, click the drop zone to add the tenant's sample files. The queue lists each job with its documents, handling mix, group, who submitted it, its status and its checks as of now, flagging jobs whose checks changed since they were submitted. Preview shows the whole job read-only with freshly re-run checks. Edit moves a queued job to Drafts and opens it in the editor; it returns to the end of the queue only when you press Submit job. Delete asks for confirmation. staff can drag jobs (or use the arrows) to change the order workers take them in; everyone else sees the order but can't change it. Running jobs stay first. Each tenant runs one job at a time. Running jobs can be previewed, and cancelled by a staff member or the person who submitted the job. A running job works through its documents on its own, a few seconds each (the document in progress shows its step, and a bar while its file is sent); “Finish run (mockup)” finishes it at once. Two sample jobs from other users are included; in one, a Media record with a matching ID was created in CollectionSpace after the job was submitted, so its preview shows a new warning. The BMU checks every document's values against CollectionSpace again when the run starts and just before creating each document: renamed terms are used under their current names (with a notice), and a document whose value no longer exists fails before anything is created for it, while the rest of the job goes on.
    • Job scheduling: jobs no longer start when they're submitted. Each tenant has a schedule of run times (by default every day at 7:00 PM, Pacific time, optionally with a time after which no new jobs start), and at each run time the queued jobs start in queue order, one at a time. A job submitted while a run is in progress waits for the next run time. Only staff (the BMU_Staff role) can change the schedule or the queue; the “BMU_Staff role” box in the top bar simulates it (ticked at first; untick it to see the read-only view an intern gets). The banner at the top of the Job queue tab shows the schedule and the next run time; staff get Schedule settings… (run days, start time, optional end time) and Pause queue… (with a reason) / Resume queue. Run days can't be more than 3 days apart, because a queued job's saved sign-in lasts 72 hours. The Runs at column shows when each job will start, and warns when that is after its sign-in expires. Staff can use Run now (next, as soon as no job is running, even outside the run times, but not while the queue is paused), Set run time… (between now and the job's sign-in expiry; Clear returns it to the schedule) and Hold / Release (a held job is skipped; its sign-in clock keeps running). Only staff can reorder the queue. Any staff member can cancel a run. Every change is written to the audit log. The mockup has no real clock for the schedule: “Demo: it's run time now” starts the due jobs one after another (use Finish run (mockup) on the running job to move on); a job's own run time starts it when that time comes while the page is open.
    • Checks while editing: each document's problems appear in its expanded row as “Must fix” (blocks submitting) or “Warning” (can proceed), and the bar under the table counts them. Submit job stays disabled until nothing needs fixing, then re-checks the whole job before adding it to the queue. “Show documents with problems” expands just those rows. Sample cases: an object number matching two objects, objects not found, duplicate IDs in CollectionSpace or within the job, TIFF quality, and dates CollectionSpace can't interpret.
    • Date: pre-filled from the image's EXIF data where there is one, and parsed the way CollectionSpace parses dates (simulated here: e.g. 2026-08-30, 1920s, circa 1850, 1901–1905, March 3, 1911). The parsed earliest/latest dates show under the field. A date CollectionSpace can't interpret must be corrected or cleared before the job can be submitted.
    • Permissions: switch the signed-in user to see options the user isn't allowed to use disabled, with the reason, and documents already set that way flagged as needing fixing. A document is also blocked when a check it needs can't run: without read on Media records (try “Imaging assistant”), or with a creator, contributor or rights holder from an authority the user can't read (try “Uploader without authority access”). Creating or editing a job needs create and update on Media records: a user without them (try “Viewer”) can view and preview jobs in Drafts, Job queue and Finished jobs, but the Create / edit job tab explains why it can't be used, and New job, Edit, Take over, Fix and reschedule, Reschedule and Delete are disabled with that reason.
    • Renaming: expand a row to edit its filename. The new name is checked as you type: safe characters only, no spaces or folders, the same file extension, unique in the job, and it must match the tenant's filename pattern (shown under the field). It's only applied once it passes, then the object number, image number, identification number and lookups are re-parsed from it. Born-digital rows get generated numbers, so they only need the general checks. Fields you've edited yourself keep your values.
    • Still open: UCJEPS locality (left out of this mockup until the herbarium decides where it belongs), BAMPFA/Cinefiles publish mapping, and whether BAMPFA and Cinefiles should get more handling options.
